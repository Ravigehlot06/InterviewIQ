# Machine Learning — Interview Readiness Estimate

## What is the ML problem?

After an interview is scored, we want a single, easy-to-understand
summary of how ready the candidate seems for a real interview at that
level: **"Interview Ready"**, **"Almost Ready"**, **"Needs Practice"**, or
**"Early Stage"**. This is a **multi-class classification** problem.

We deliberately call this an **"Interview Readiness Estimate"**, not a
measurement of employability — it is a practice-oriented signal derived
from interview performance data, not a validated psychometric or hiring
tool.

## What is the dataset?

`backend/ml/data/interview_performance.csv` — currently **SYNTHETIC /
DEMO DATA**, generated by `backend/ml/generate_demo_dataset.py`. Each row
represents one completed interview with:

| Column | Type | Meaning |
|---|---|---|
| `technical_score` | float 0-100 | Average technical evaluation score |
| `communication_score` | float 0-100 | Average communication score |
| `problem_solving_score` | float 0-100 | Average problem-solving score |
| `confidence_score` | float 0-100 | Average confidence score |
| `answer_quality` | float 0-100 | Average answer relevance score |
| `questions_answered` | int | Number of questions answered |
| `overall_score` | float 0-100 | Weighted overall score |
| `difficulty` | categorical | easy / medium / hard |
| `experience_level` | categorical | fresher / 0-2 / 2-5 / 5+ |
| `interview_type` | categorical | hr / technical / role_based / company |
| `readiness_label` | categorical (target) | Interview Ready / Almost Ready / Needs Practice / Early Stage |

**This dataset is explicitly synthetic.** Once enough real
`PerformanceMetric` rows accumulate in production (one row is written per
completed interview — see `app/models/performance_metric.py`), export
that table to CSV in the same column format and replace
`interview_performance.csv` with it, then re-run `train.py`.

## What is a "feature"? What is the "target"?

A **feature** is an input the model uses to make a prediction (the seven
numeric columns + three categorical columns above). The **target** is
what we're trying to predict: `readiness_label`.

## Why Random Forest?

- Handles a mix of numeric and categorical (label-encoded) features well.
- Robust to the noise/variance inherent in subjective interview scoring.
- `class_weight="balanced"` mitigates any class imbalance in demo data.
- Provides a strong, explainable baseline — an ensemble of decision trees
  is easy to reason about in a viva ("it's voting across many small
  decision trees built on random subsets of the data").
- No heavy tuning or GPU requirement, unlike deep learning — appropriate
  for the dataset size and project scope.

## Pipeline: dataset → cleaning → features → train → evaluate → save

`backend/ml/train.py`:

1. **Load** `ml/data/interview_performance.csv` (`load_dataset`)
2. **Validate columns** (`validate_columns`) — fails fast with a clear
   error if a required column is missing
3. **Clean** (`clean`) — drops rows with missing required values, clips
   scores to valid ranges
4. **Encode** (`encode`) — `LabelEncoder` for `difficulty`,
   `experience_level`, `interview_type`, and the target `readiness_label`
5. **Split** — 80/20 train/test, stratified by label
6. **Train** — `RandomForestClassifier(n_estimators=200, max_depth=8,
   class_weight="balanced", random_state=42)`
7. **Evaluate** — accuracy, weighted precision/recall/F1, confusion
   matrix, printed to console
8. **Save** — `joblib.dump({model, encoders, feature_cols, metrics})` to
   `ml/models/readiness_model.joblib`

### Commands

```bash
cd backend
python ml/generate_demo_dataset.py   # (re)generate the synthetic dataset
python ml/train.py                    # train + save the model
python ml/evaluate.py                 # re-evaluate a saved model
python ml/predict.py                  # quick standalone inference demo
```

### Honest note on metrics

On the synthetic dataset, `readiness_label` was derived directly as a
deterministic function of `overall_score` during data generation (see
`_readiness_label()` in `generate_demo_dataset.py`), and `overall_score`
is itself one of the model's input features. This makes the reported
accuracy on synthetic data unrealistically high (commonly >99%) — it
mainly proves the pipeline works correctly end-to-end, **not** that the
model has learned a subtle real-world pattern. Once trained on real
production data (where readiness is more genuinely a judgment call), we
would expect materially lower, more realistic metrics. Do not present the
synthetic-data metrics as evidence of real-world accuracy in a viva —
present them as a pipeline correctness check, and explain this
limitation directly if asked.

## How is the saved model loaded and used?

`backend/ml/predict.py` exposes `predict_readiness(features, model_path)`:
loads (and caches) the joblib artifact, encodes the incoming feature dict
using the *same* fitted encoders used at training time (falling back to
the first known class for any unseen category), and returns
`(label, confidence_percent)`.

`backend/app/services/ml_service.py` wraps this for the Flask app:

```python
get_readiness_estimate(features) -> {"readiness_label", "readiness_score", "source"}
```

If the model file doesn't exist yet (e.g. `train.py` hasn't been run), it
falls back to a simple rule-based readiness estimate from `overall_score`
alone, tagged `"source": "fallback"` so the frontend can show that this
isn't the trained model's output.

## How does Flask call it, and how does the frontend show it?

`interview_routes.py`'s `complete_interview()` computes aggregate scores
from all evaluations, calls `get_readiness_estimate()`, and saves the
result on the `Report`. The frontend's `Report.jsx` page displays
`readiness_label` with a badge indicating whether it came from the
**ML model** or the **fallback** rule, plus a note that this is a
practice readiness estimate, not an employability measurement.

There is also a standalone endpoint, `POST /api/ml/predict`, for manual
testing/demonstration of the model independent of a full interview flow.
